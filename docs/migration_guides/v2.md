# Migration Guide for v2

Migrating from `1.x` (`1.4.2`) to the latest `2.x` (`2.3.0`). Only `v2.1.0` is tagged; `2.0.0`–`2.3.0` are `setup.py` bumps.

## Required changes

- **`PydanticMixin` import**: the module was split. `eventsourcing_helpers.message.PydanticMixin` → `eventsourcing_helpers.message.pydantic.PydanticMixin`.
- **`pydantic` is an extra**: it is no longer a hard dependency. If you use `PydanticMixin`, `pip install eventsourcing-helpers[pydantic]` (`pydantic>=2`).
- **Old mock `add_message(message_class=..., data=...)` API**: the default `mock` backend keeps the `1.4.2` `key`/`value` API. To keep the pre-1.4.2 seed style, use `mock_compat` / `backend_compat.MockBackend`.

### Migration steps

1. If you use Pydantic messages, install the extra and change the import:

   ```python
   # Before (1.x)
   from eventsourcing_helpers.message import PydanticMixin

   # After (2.x)
   from eventsourcing_helpers.message.pydantic import PydanticMixin
   ```

2. If tests still seed the bus with `message_class`/`data`, point the backend at the compat class:

   ```python
   # Before (old mock)
   # eventsourcing_helpers.messagebus.backends.mock.MockBackend
   messagebus.consumer.add_message(
       message_class="UpdateArticleStock", data={"id": "<article-id>"}
   )

   # After (2.x) — keep that call style
   # eventsourcing_helpers.messagebus.backends.mock.backend_compat.MockBackend
   # or MessageBus backend alias "mock_compat"
   ```

   If you already migrated tests to `add_message(key=..., value=...)` on `1.4.2`, keep the default `mock` backend.

## Optional changes

- **`PydanticMixin` extra fields** (`2.1.0`): `extra` is `"ignore"` (was `"forbid"`) so unknown payload fields no longer fail validation.
- **Custom DTO deserializers** (`2.2.0`): register an event **class** (not only a class-name string) in `EventHandler.handlers` to deserialize into that type via `from_message_to_dto(..., deserialize_class=...)`.
- **Mock dict headers** (`2.2.1`): `create_message` / `add_message` accept a headers **dict** as well as a list of pairs.
- **Mock `stop_on_eof`** (`2.3.0`): set `config["consumer"]["stop_on_eof"]` (default `True`) to keep the mock consume loop running when the queue is empty.

## Opt in to Kafka batch processing

Existing `consume()` workers can stay unchanged. Choose one consumer mode per
worker.

In the existing message bus config, set these consumer options under
`backend_config.consumer` (keep the application's topics, brokers and schema
registry settings):

```python
config["backend_config"]["consumer"].update({
    "enable.auto.commit": False,
    "enable.auto.offset.store": False,
})
```

Remove single-message `poll_timeout` / `non_blocking` options and experimental
`batch_max_size` / `batch_max_wait` keys from the batch worker's config. Pass
`batch_size` and `timeout` to `consume_batch()` instead.

### Reuse an existing handler

With the application's existing message bus and `Handler` instance:

```python
from eventsourcing_helpers.consumer import Consumer

consumer = Consumer(messagebus, handler)
# Before: consumer.consume()
consumer.consume_batch(batch_size=100, timeout=0.1, delivery_timeout=30.0)
```

The default `Handler.handle_batch()` calls `handle(message)` in supplied order,
inside each message's `process()` context. Existing `messagebus.produce()` calls
keep the correct input headers and trace. This batches acknowledgement, not
database operations: override `handle_batch()` to do actual bulk processing.

### Process and publish in bulk

Alternatively, pass a batch callable directly to the bus. This example assumes
the application's existing `bulk_write` and schema-appropriate `build_event`:

```python
def handle_batch(messages):
    bulk_write([message.value for message in messages])
    messagebus.produce_many([
        {
            "key": source._meta.key,
            "value": build_event(source),
            "source": source,
        }
        for source in messages
    ])


messagebus.consume_batch(
    handle_batch, batch_size=100, timeout=0.1, delivery_timeout=30.0
)
```

Keep the input message as `source` for each output so its propagated business
headers and incoming trace follow it. Explicit output headers take precedence.
When a custom bulk handler calls an existing per-message handler instead, wrap
each call in `with message.process():`. Without either, output uses the batch
context, not any one input's business headers.

The managed Kafka loop confirms **all** output on its producer, including ordinary
`produce()` calls, before marking handled inputs in the offset watchdog and
committing the fetched batch. Do not add your own delivery scope or offset commit
inside the handler. Per-call polling/flushing is deferred to the batch's delivery
scope, even when the producer's `flush` setting is true. Outside managed batches,
publishing still follows the configured flush policy.

### Timeouts, replay and manual loops

- `batch_size` is a maximum; short batches are normal and empty reads do not
  invoke the handler. `timeout` is the native fetch timeout in seconds
- `delivery_timeout` starts before the handler runs and bounds producer queue
  waits and delivery confirmation. It cannot interrupt database calls. Keep
  processing within Kafka's `max.poll.interval.ms`
- Handler or delivery failures stop the loop without committing that batch.
  Commit failures also propagate. Previously completed writes/publications can
  replay: make application effects replay-safe; this is not a transaction
- Preserve supplied order within each partition. Join workers and propagate
  their errors before returning, activate message context inside workers, and
  do not share the producer with unrelated work during a batch
- `get_batch_consumer()` returns a factory for a manual loop. Use
  `with consumer_factory() as consumer:` and call `commit_batch(batch)` only
  after handling and confirming output yourself; the managed barrier applies
  to `consume_batch()`, not manual iteration
- Both mock backends support batches and per-partition offsets. Test failed
  batches and replay as well as successful output; mocks do not prove broker
  delivery. See the [runnable mock example](../../MIGRATION.md#opt-in-to-kafka-batches)
