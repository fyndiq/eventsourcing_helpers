# Migration Guide for v1

Migrating from `0.8` (`v0.8.13`) to the latest `1.x` (`1.4.2`). There are no `v1.*` git tags; versions are taken from `setup.py`.

## Required changes

- **`confluent-kafka-helpers` 1.x** (`1.0.0`): require `confluent-kafka-helpers>=1.0.0` (`==1.0.0.dev0` at the `1.0.0` bump, then relaxed). This is the Kafka/OTel stack this line is built on.
- **`pydantic>=2` becomes a hard dependency** (`1.1.0`) even if you do not use `PydanticMixin`.
- **Mock `Consumer.add_message` signature** (`1.4.2`): `add_message(message_class=..., data=...)` → `add_message(key=..., value=...)`. The `mock` backend class path is `...mock.backend.MockBackend` (no longer `...mock.MockBackend`).
- **Mock producer records the serialized envelope** (first released in `1.2.0`): `MockBackend.produce` serializes a `Message` / `PydanticMixin` DTO before recording it, so the producer holds `{"key": ..., "value": {"class": ..., "data": {...}}}` instead of the DTO. Assertions that pass a DTO as `value` now compare a `Message` against a `dict` and fail with `AttributeError: 'dict' object has no attribute '__dict__'`. Build the expected message as an envelope dict instead.

### Migration steps

Before editing any test, choose this service's path — see **Choosing a test path** below. Steps 2-5 are the full migration. A service on the compat backend does step 1, then the compat step only.

1. Upgrade `confluent-kafka-helpers` to 1.x and install `pydantic>=2`.
2. Update mock consumers that seed messages:

   ```python
   # Before (0.8 / 1.0-1.4.1)
   messagebus.consumer.add_message(
       message_class="UpdateArticleStock", data={"id": "<article-id>"}
   )

   # After (1.4.2)
   messagebus.consumer.add_message(
       key="<article-id>",
       value={"class": "UpdateArticleStock", "data": {"id": "<article-id>"}},
   )
   ```

3. Change every expected message from a DTO to an **envelope dict**. This is a change of data, not of structure — keep whatever shape the service already uses. If it builds messages inline, keep them inline; if it has builder functions, change what they return. Do not add builders to a service that has none, and do not inline the ones a service already has.

   ```python
   # Before — inline DTO
   expected_event = events.ArticleReviewUpdated(id=article_id, action="CREATED", stars=5)

   # After — inline dict, same place in the test
   expected_event = {
       "key": article_id,
       "value": {
           "class": "ArticleReviewUpdated",
           "data": {"id": article_id, "action": "CREATED", "stars": 5},
       },
   }
   ```

   ```python
   # Before — builder returning a DTO
   def build_article_review_updated_event(article_id, **data):
       return events.ArticleReviewUpdated(id=article_id, action="CREATED", stars=5, **data)

   # After — same builder, returns the dict
   def build_article_review_updated_event(article_id, **data):
       return {
           "key": article_id,
           "value": {
               "class": "ArticleReviewUpdated",
               "data": {"id": article_id, "action": "CREATED", "stars": 5} | data,
           },
       }
   ```

   Include `topic` / `headers` in the dict when the test asserts them; the producer records whatever keyword arguments `produce` was called with.

   Never serialize a DTO to produce the expected value — tests describe the message on the wire.

4. Replace the deprecated producer assertions with `assert_messages_produced_with`, which compares the **whole produced list, in order**:

   | Deprecated | Use |
   |---|---|
   | `assert_one_message_produced_with(key=..., value=...)` | `assert_messages_produced_with([expected])` |
   | `assert_multiple_messages_produced_with([...])` | `assert_messages_produced_with([...])` |

   Both of those already asserted the complete output. `assert_one_message_produced_with` swaps directly. `assert_multiple_messages_produced_with` checked the count and that each message was present, but **not the order** — so put the expectations in production order.

   **`assert_message_produced_with` does not.** It asserted *membership* — that one message was somewhere in the list — so it silently tolerated messages the test never named. Swapping it for `assert_messages_produced_with([expected])` compares the full list against a single message and fails on everything else the test produced. Its presence is the signal that the test produces more than one message; otherwise the author would have used `assert_one_message_produced_with`.

   Read what the test means before converting it. There are two cases.

   **(a) The extra messages come from arrange steps.** The test sets up state, then exercises the behaviour it is actually about. Clear the producer between the two, so the assertion sees only the message under test:

   ```python
   # Before — membership, ignoring whatever the setup produced
   await test_client.post("/api/v1/SE/reviews", json=review_created_webhook)
   await test_client.post("/api/v1/SE/reviews", json=review_updated_webhook)
   messagebus.producer.assert_message_produced_with(key=key, value=expected_event)

   # After — arrange, clear, act, assert
   await test_client.post("/api/v1/SE/reviews", json=review_created_webhook)
   messagebus.producer.clear_messages()

   await test_client.post("/api/v1/SE/reviews", json=review_updated_webhook)
   messagebus.producer.assert_messages_produced_with([expected_event])
   ```

   This keeps the test asserting exactly what it asserted before. `clear_messages()` exists on both mock backends. For isolation *between* tests, prefer an autouse fixture over a call in each test body:

   ```python
   @pytest.fixture(autouse=True)
   def messagebus_reset(messagebus):
       yield
       messagebus.producer.clear_messages()
   ```

   **(b) The test means to assert the whole output.** A loop over expected messages becomes a single call:

   ```python
   # Before — membership, one at a time
   for expected_event in expected_events:
       messagebus.producer.assert_message_produced_with(key=key, value=expected_event)

   # After — the whole list, in production order
   messagebus.producer.assert_messages_produced_with(expected_events)
   ```

   Here the new form is stricter than the old one: it also catches extra messages and a changed order. That is the point — check the order the service actually produces in rather than reordering the expectations until it passes.

   `assert_no_messages_produced`, `assert_one_message_produced` and `assert_num_messages_produced` are not deprecated; keep or adopt them for count-only assertions.

   This applies to **every** comparison against a produced message, including raw ones that never call a helper:

   ```python
   assert messagebus.producer.messages[-1] == expected_event
   ```

   Grep for `value=` next to `producer.` — a suite that stops at the first failure will hide the rest.

5. If you set the backend as a full class path, point it at `eventsourcing_helpers.messagebus.backends.mock.backend.MockBackend` (the `mock` alias still works).

### Choosing a test path

The full migration is the default. When the test changes are large enough to dominate the upgrade, a service may stay on the old interface by switching to the **compat backend** instead. Decide before editing, and record the choice.

1. Count what must change: producer assertions comparing against a DTO, `consumer.add_message(message_class=..., data=...)` calls, and raw comparisons against `producer.messages`.
2. **Full migration** when that work sits in one or two test files and the service does not seed consumer messages throughout its suite.
3. **Compat backend** when consumer seeding is spread across the suite, when the DTOs come from factories shared with non-test code, or when the count runs to dozens of sites across many files.

To use the compat backend, change only the backend path — `mock_compat`, or `eventsourcing_helpers.messagebus.backends.mock.backend_compat.MockBackend`:

```python
KAFKA_MESSAGEBUS_CONFIG = {
    "backend": "eventsourcing_helpers.messagebus.backends.mock.backend_compat.MockBackend",
    "backend_config": {},
}
```

It keeps the pre-1.x interface: `add_message(message_class=..., data=...)`, the old `assert_*_produced_with` helpers, and DTOs recorded unserialized. Steps 2-4 do **not** apply — leave the tests as they are.

**It is all or nothing.** The compat backend has no `add_messages`, `assert_messages_produced_with`, `assert_num_messages_produced`, `assert_messages_produced_with_class_names` or `num_messages`, so none of the new fixtures or assertions work with it. In particular the `consume_messages` fixture calls `consumer.add_messages(...)` and is unavailable — a service on compat keeps its own consumer wiring. Do not mix the two interfaces.

`shop-article-handler-service`, `sold-articles-projection-service` and `qliro-integration-service` took this path.

### A fully migrated suite

`article-handler-service` (`tests/integration/command_handler/`) is one example of the end state — a suite that keeps its message builders in `commands.py` / `events.py`. The builders are that service's own structure, not a requirement:

- Override the plugin's `consumer` fixture to return the application's consumer; `messagebus` and `consume_messages` then come from the `pytest11` entry point — no local mock wiring.
- Commands and events are envelope dicts (step 3). No DTOs anywhere in the test path, and no serializer imports.
- Drive a test with `consume_messages([...])`, then assert the full output with `messagebus.producer.assert_messages_produced_with([...])`.
- Clear state between tests with an autouse fixture calling `messagebus.producer.clear_messages()`.

## Optional changes

- **OpenTelemetry spans** (`1.0.0`): command/event handlers emit OTel spans via `eventsourcing_helpers.tracing` — no call-site change unless you customize the tracer.
- **`PydanticMixin`** (`1.1.0`): frozen Pydantic v2 models with `to_dict()` / `_class` — use when commands/events should be Pydantic models. Import from `eventsourcing_helpers.message` on this line.
- **Pytest plugin** (`1.1.0`): fixtures `consumer`, `messagebus`, `consume_messages` via the `pytest11` entry point. See **A fully migrated suite** above for how a migrated suite uses them.
- **`assert_num_messages_produced`** (`1.3.0`) and **`assert_messages_produced_with_class_names`** (`1.4.0`): extra mock producer assertions, for when you only care about the count or the class names.
- **Producing to an explicit topic** (`1.4.2`): the mock producer records `topic` alongside `key` / `value`, so add it to the expected envelope dict when a test asserts it (step 3).
